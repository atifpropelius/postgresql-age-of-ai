## The one example and its boundaries

Atif signs in, creates a private task, uploads a PDF and sees an update on another screen. A task row belongs in `public.tasks`; the PDF's **bytes** belong in object storage, with metadata in Postgres and optionally a path in the task row. Auth establishes his identity. Grants and RLS decide task-row access. A Realtime subscriber gets a change only when that flow is configured. Supabase Auth generates its own confirmation, invite, magic-link/OTP and password-reset emails; a configured SMTP provider delivers them. An application email such as “task assigned” is a separate workflow: an Edge Function or other trusted backend can call a mail provider with a server-only credential. A database function invoked by `rpc()` executes **inside Postgres** and uses its database compute and connection capacity; it is not an Edge Function. [Auth email templates](https://supabase.com/docs/guides/auth/auth-email-templates), [custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

**Data API:** PostgREST exposes allowed database tables, views and functions as HTTP routes. **OpenAPI:** a machine-readable description of the exposed API; it documents routes but does not execute them. A direct client call is suitable only when grants and tested RLS policies protect the object. Use trusted server code for privileged operations, external secrets and appropriate custom workflows.

**Three possible request entry points:** For the five-minute demo, choose the **Data API** for a simple task-row read: client → generated API → Postgres. An **Edge Function** can instead receive a custom HTTP request, run application logic, and call the Data API or connect to Postgres. A **Supabase Compute HTTP service** could be another entry point in the future, but Compute remains Private Alpha for internal evaluation, cannot serve production or end customers during the preview, and this project has no access. These are alternatives for the HTTP entry point, not three required hops for one request. Verify the caller and authorize the requested row in each design. A user-scoped Supabase client enforces that user's RLS policies; a privileged server client bypasses RLS, so never assume an Edge Function or backend automatically protects task rows. [Data API](https://supabase.com/docs/guides/api), [Edge Functions](https://supabase.com/docs/guides/functions), [securing Edge Functions](https://supabase.com/docs/guides/functions/auth), [Compute preview](https://supabase.com/compute).

**Three meanings of compute:** **Database compute** is the CPU and RAM used by the project's Postgres instance; `rpc()` runs there. **Edge Functions** are a separate managed runtime for HTTP handlers. The new **Supabase Compute** product is designed for isolated, longer-running web services, jobs and agent sandboxes next to project data, but as of this review it is in **private alpha** with a waitlist. Supabase limits the preview to internal evaluation and says it must not serve production workloads or end customers. The supplied screenshot explicitly says this project has no access yet. For production services that need a dedicated always-on runtime today, continue evaluating an external backend such as EC2, Render or another service. [Supabase Compute](https://supabase.com/compute), [October 2026 announcement](https://supabase.com/blog/select-2026-build-anything), [database compute usage](https://supabase.com/docs/guides/platform/manage-your-usage/compute).

**Slide 8, Compute in 90 seconds:** Supabase says Compute can run a Node.js or Deno service, a static binary or a Dockerfile-defined custom runtime in a full Linux environment, close to the project database. It describes public HTTP services and private services without an HTTP endpoint for queue jobs or agent sandboxes. These support a queue consumer, bulk PDF processing, an AI agent or another long-running task; Supabase says Compute services have no wall-clock execution limit. **Persistent service** here means a deployed service configuration and endpoint, not a guarantee that one process stays in memory forever: Supabase says idle services can suspend and resume. Do not promise durable local disk, preserved in-memory state, a specific uptime guarantee, or pricing that the preview terms do not establish. [Compute product page](https://supabase.com/compute), [Supabase announcement](https://supabase.com/blog/select-2026-build-anything).

An **Edge Function** is a Deno-based request handler with hosted runtime limits; it can also perform bounded background work during its worker lifetime, so “background work” is not exclusive to Compute. A **VPS/EC2 instance** is a separately operated server: it gives the team greater control of OS, runtime and deployment, with corresponding hosting and operational responsibility. Supabase Compute aims to place suitable app services beside Postgres and Supabase Auth/Storage, but the current **private alpha is for internal evaluation only** and the supplied project screenshot says **no access yet**. Keep production consumers and other long-running jobs on an existing external backend for now. No Compute product price, general-availability date, production support commitment or local-disk guarantee is verified here. [Edge Function limits](https://supabase.com/docs/guides/functions/limits), [Compute preview terms](https://supabase.com/compute), [Supabase announcement](https://supabase.com/blog/select-2026-build-anything).

**Slide 9, optional Cloudflare gateway:** `Client → api.example.com → Cloudflare Worker rate check → Supabase Edge Function / protected API → PostgreSQL`. A Worker runs on Cloudflare, outside Supabase. It can return HTTP 429 before a request reaches an expensive function or RPC. A Worker Custom Domain can attach `api.example.com` when the domain is in an active Cloudflare zone; this is a proxy endpoint, **not** Supabase's own paid Custom Domains add-on. It does not automatically rebrand every Auth callback, Storage URL, WebSocket or Supabase API route; proxy compatibility must be designed and tested. A Worker route can also transform or forward requests, but keep the example focused on early rejection. Use a server-verified identity or an appropriately chosen route/key for limits. Never trust a user ID supplied by the client, and keep Supabase secret keys on the server. The original Supabase URL may remain reachable: if callers can bypass the Worker, the edge check protects only traffic that uses the custom domain. Continue enforcing Supabase Auth, grants and RLS. [Cloudflare Worker Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/), [rate-limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [Supabase Custom Domains](https://supabase.com/docs/guides/platform/custom-domains), [Data API security](https://supabase.com/docs/guides/api/securing-your-api).

**Cloudflare limits and cost for questions:** Workers Free currently includes 100,000 Worker requests per day and 10 ms CPU time per invocation. At the daily limit, a **fail-open** route can bypass the Worker; choose **fail-closed** for a security-critical gate, accepting that requests may be rejected instead. Workers Paid has a minimum charge of **$5 USD per account per month**, with included usage and additional request/CPU charges above it; $5 is **not** a hard monthly cap. The Workers Rate Limiting binding is local to each Cloudflare location and intentionally approximate, so it is suitable for reducing abuse but not exact global accounting. Workers KV is eventually consistent and is not a strict global counter. Recheck the plan and prices before presenting. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [Worker limits and fail mode](https://developers.cloudflare.com/workers/platform/limits/), [rate-limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/).

**Free versus Pro:** Free is useful for learning and low-stakes prototypes; a production service needs an availability, backup, support and capacity decision. Current plan terms and add-on costs change. Use the [pricing page](https://supabase.com/pricing), [billing guide](https://supabase.com/docs/guides/platform/billing-on-supabase) and [Usage guide](USAGE-GUIDE.md) instead of quoting a fixed bill on stage. If the app needs a dedicated backend, Supabase can still be its database/Auth/Storage layer.

**Spend Cap talk track:** On Pro, the Spend Cap starts enabled by default. With it on, covered usage over the plan quota can bring notification, a grace period and service restrictions; it is not a promise that the entire invoice cannot rise. Turning it off allows covered usage to continue past allowances with billable overages. Database compute and branching compute are outside the Spend Cap, and Supabase says branch usage is not covered. Before changing it, check the organization's Usage page, Upcoming Invoice and expected traffic. The control is in the organization's **Billing → Cost Control** area, not an individual project setting. [Billing FAQ](https://supabase.com/docs/guides/platform/billing-faq), [Cost Control](https://supabase.com/docs/guides/platform/cost-control), [branching usage](https://supabase.com/docs/guides/platform/manage-your-usage/branching).

## Production habits to explain on slide 19

- **Protect dashboard access:** Supabase account MFA currently uses TOTP and does not supply recovery codes. Enrol a second factor in a different app or device, then verify it works while the primary still works. For a non-SSO account, Supabase says it cannot restore account access if every factor is lost. A second organization owner helps the team retain project administration; it does **not** recover the locked personal account. A useful personal line is: “I lost access for a month; set up the backup before you need it.” [Account MFA](https://supabase.com/docs/guides/platform/multi-factor-authentication), [lost factor](https://supabase.com/docs/guides/troubleshooting/lost-accessforgot-the-mfa-device-nAPT-7), [organization access](https://supabase.com/docs/guides/platform/access-control).
- **Change schema through migrations:** Create and test a versioned migration for each table, column, view or policy change before applying it remotely. Supabase advises local Dashboard edits can be captured with `db diff`; changing the remote SQL/Table Editor directly bypasses migration history and may break the next `db push`. [Database migrations](https://supabase.com/docs/guides/deployment/database-migrations).
- **Triage Security Advisor:** Review errors and warnings, especially after Auth, RLS or schema changes. Read the affected object and recommended fix, decide whether the finding is real or intentional, and rerun the check after a change. A zero-error screenshot can still show warnings; a finding alone does not prove a breach. [Advisors](https://supabase.com/docs/guides/observability/advisors).
- **Watch Logs and Observability:** After each release and on a regular team cadence, filter Logs by the right project, time window, service and error level; inspect status and message, then verify a fix. Check query performance, connections, resource pressure and service health for changes. Advisor findings flag possible configuration issues; error logs record runtime events, so review both. Use these signals alongside application behavior and user reports. [Observability](https://supabase.com/docs/guides/observability), [Logs in Studio](https://supabase.com/docs/guides/observability/logs).
- **Start with official Developer Docs:** Look up product behavior, commands, plan limits and troubleshooting in [Supabase Developer Docs](https://supabase.com/docs) before relying on old screenshots or third-party posts. The Studio menu and service details evolve.

**Edge Function coding note for slide 7:** Edge Functions are TypeScript on a Deno runtime. Supabase documents Express, Oak and Hono as optional ways to route several HTTP paths inside one function; the framework is a coding style choice, not a switch to a Node/EC2 server. A small single-action function can use a plain handler. Use clear routes, validation and useful error logs so failures are easier to locate in Studio. [Edge Function quickstart](https://supabase.com/docs/guides/functions/quickstart), [routing](https://supabase.com/docs/guides/functions/routing), [logging](https://supabase.com/docs/guides/functions/logging).

## Accuracy notes for questions

- A Supabase project contains managed PostgreSQL compute. The platform manages its infrastructure; `rpc()` runs SQL in that database. An Edge Function runs in a separate regional runtime. The newly named Supabase Compute product targets longer-running services but is currently a private alpha for internal evaluation only; do not confuse it with database compute or recommend it for production yet. [Database functions](https://supabase.com/docs/guides/database/functions), [Edge Functions](https://supabase.com/docs/guides/functions), [Supabase Compute](https://supabase.com/compute).
- A temporary Supabase branch is an isolated preview environment, normally without production rows or Storage objects. Secrets and third-party callbacks need deliberate setup. For a brief test, a preview branch can reduce cost compared with keeping a separate test project active all month. It has no fixed branch fee, but Supabase charges for its compute and other usage; branching compute credits do not apply. A persistent branch stays active and is not automatically cheaper than a separate project. Compare compute size, active hours and other usage before making the cost claim for your own setup. Preview branches are normally deleted when their pull request closes; delete unused branches created through other workflows. Availability depends on the plan. [Branching](https://supabase.com/docs/guides/deployment/branching), [branching usage](https://supabase.com/docs/guides/platform/manage-your-usage/branching), [compute usage](https://supabase.com/docs/guides/platform/manage-your-usage/compute).
- The region controls primary project data location. “Nearest” does not settle contractual compliance. Changing the region requires a new project and migration. [Regions](https://supabase.com/docs/guides/platform/regions), [region change](https://supabase.com/docs/guides/troubleshooting/change-project-region-eWJo5Z).
- Usage charts and Observability serve different questions. Usage describes accumulated consumption and allowances; Observability and Logs help diagnose a specific incident. A chart may update after the event, so check its time window. [Usage](https://supabase.com/docs/guides/platform/manage-your-usage), [Observability](https://supabase.com/docs/guides/observability).
- A browser tab is not necessarily a PostgreSQL session. Realtime WebSocket clients, API requests and database connections are different measures. [Realtime peak connections](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-peak-connections), [connection management](https://supabase.com/docs/guides/database/connection-management).
